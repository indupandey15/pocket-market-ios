# PocketMarket

A small iOS marketplace app (SwiftUI) demonstrating offline-first architecture:
browse a catalog of listings in a grid, favorite items, create new listings
while offline, and watch them sync automatically when connectivity returns.

---

## 1. Setup — opening this in Xcode

Double-click `PocketMarket.xcodeproj` (or `open PocketMarket.xcodeproj`) and
it should build and run directly — both the `PocketMarket` app target and the
`PocketMarketTests` unit test target are already wired up, with
`listings_200.json` bundled as a resource and the `.xcdatamodeld` set to
`codeGenerationType="class"` (so `ListingEntity`/`PendingChangeEntity` are
generated automatically — no manual `NSManagedObject` subclasses needed).

This project uses Xcode 16's file-system-synchronized groups
(`PBXFileSystemSynchronizedRootGroup`) rather than a hand-maintained
`project.pbxproj` — any `.swift` file added to the source folders on disk is
picked up by Xcode automatically, no "Add Files to Project" step required.

**Before your first build**, Xcode may ask you to pick a signing team
(Project → Signing & Capabilities → your Apple ID) since `DEVELOPMENT_TEAM`
isn't set in a portable project file — this is normal for any fresh project
and takes one click.

Build target: iOS 17+ (uses `NavigationStack`, `.task(id:)`, Swift Concurrency
throughout). Run on a simulator — no backend or API key required, everything
runs against the bundled JSON + on-device Core Data.

**To demo the offline flow:** run on a simulator, turn off Wi-Fi (toggle it
from the Mac's menu bar if running on the iOS Simulator, or Airplane Mode on
a device), favorite a few items and create a new listing, then turn
connectivity back on. Within about 10 seconds the sync status banner picks
up the reconnect and drains the queue — see "Why ~10 seconds" below.

## 2. What's implemented

| Feature | Where |
|---|---|
| Local DB & full persistence | Core Data (`Data/Persistence/`) — `ListingEntity`, `PendingChangeEntity` |
| Queue offline creates/edits | `PendingChangeEntity` + `SyncEngine` drains oldest-first on reconnect |
| Conflict resolution | `ConflictResolver.swift` — last-write-wins by `version`, falling back to `updatedAt` |
| Sync status shown | `GlobalSyncStatusView` (top banner) + per-card `SyncStatusBadge`, with an explicit `.syncing` state so the UI never jumps silently from Pending to Synced |
| Efficient image caching + thumbnails | `ImageCacheService` — memory (`NSCache`) + disk tiers, `ImageIO` downsampling at decode time |
| Camera / photo picker | `CameraCaptureView.swift` (`UIImagePickerController`) + `PhotoLibraryPickerView.swift` (`PHPickerViewController`, no Photos permission required) |
| Background upload on reconnect | `Reachability` → `SyncEngine.syncIfPossible()`, plus a periodic reachability probe (see below) |
| Input validation | `CreateListingViewModel.validate()` — title/price/description bounds |
| Secure token storage | `KeychainService.swift` (no auth in this mock API, but wired for when there is one) |
| Clear separation of layers | Domain (pure models/protocols) → Data (Core Data/network/sync, all behind protocols) → Presentation (SwiftUI + ViewModels) |
| 200 listings, smooth grid | `listings_200.json` (generated by `Scripts/generate_mock_listings.py`), `LazyVGrid` |
| Unit tests | `PocketMarketTests/` — conflict resolution, validation, view model filtering |

## 3. The 200-item mock data

`Resources/listings_200.json` was generated by `Scripts/generate_mock_listings.py`
(re-run with `python3 generate_mock_listings.py` to regenerate). Each listing
has a real, resolvable image URL via `picsum.photos/seed/{n}/{size}` —
deterministic per listing so caching behavior is honestly demonstrable
(same seed = same image = a real cache hit, not a placeholder gray box).

`BundledJSONNetworkService` reads this file and simulates realistic network
latency (500ms). The failure rate is set to 0% so the demo flow completes
cleanly; adjust `failureRate` in `AppContainer.swift` to exercise the
error/retry UI paths. Swap in `NetworkService` (already written, same
protocol) to point at a real hosted mock with zero other code changes.

`generate_mock_listings.py` and `generate_xcodeproj.py` are dev-only tools —
neither ships inside the compiled app (check Target Membership if a script
ever ends up in a build phase by accident).

## 4. Why ~10 seconds to detect a reconnect

`NWPathMonitor`'s long-lived monitor does not reliably fire a "back online"
event on the iOS Simulator specifically — a real platform quirk hit during
development, not a hypothetical edge case. `Reachability.recheckConnectivity()`
starts a fresh one-shot `NWPathMonitor` probe on a 10-second timer
(`SyncEngine`'s `init`) to catch the missed transition. On a physical device
this fallback rarely matters since the primary monitor is reliable there;
it stays in as a safety net either way.

## 5. Performance & memory considerations

- **Grid virtualization**: `LazyVGrid` only builds/renders cells near the
  viewport — off-screen cells and their images don't exist in memory.
- **Decode-time downsampling**: images are decoded directly at the target
  cell size using `CGImageSourceCreateThumbnailAtIndex`, never fully
  decoded at source resolution and then scaled down. This is the single
  biggest lever — an 800×800 source image decoded for a 170×170 cell costs
  a fraction of the memory a naive `UIImage(data:)` would.
- **Two-tier cache**: `NSCache` (auto-evicts under memory pressure) backed
  by a disk cache (so a cold relaunch doesn't re-download all 200 images).
- **Cancellation**: `CachedAsyncImageView` cancels its load task in
  `onDisappear`, so fast scrolling doesn't pile up orphaned decodes.
- **Core Data on a background context**: all reads/writes happen off the
  main thread via a single serial `backgroundContext`; the UI only touches
  published `Listing` value types.

---

## 6. Trade-offs

- **Sync retry** is immediate-on-reconnect with a retry counter recorded per
  pending change, but there's no exponential backoff — acceptable for a
  demo-scale queue, would matter more under sustained server errors.
- **No pagination** — 200 items load in one shot. At 10,000+ items,
  `fetchListings()` would need cursor/offset pagination and the disk image
  cache would need real LRU with byte-size accounting instead of the
  current simpler approach.
- **No real backend** — `BundledJSONNetworkService` stands in for a REST
  API. `NetworkService.swift` shows the real-HTTP-client shape, same
  protocol, ready to point at one.
- **Conflict resolution** is last-write-wins by version (falling back to
  timestamp), not a field-level merge — the right scope call here; a
  production marketplace with concurrent edits would want per-field merge.
- **Single serial `backgroundContext`** for all Core Data writes is
  correctness-safe (deterministic write ordering matters for sync) but
  becomes a throughput bottleneck at higher concurrent-write volume.
